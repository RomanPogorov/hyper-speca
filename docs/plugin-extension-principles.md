# Принципы расширяемости Hyper

Статус: принципиальное направление; конкретные контракты и полный lifecycle ещё обсуждаются. Описание текущего runtime и плана доставки: [plugin-runtime-architecture.md](plugin-runtime-architecture.md); инструкция автору плагина: [src/plugins/SKILL.md](../src/plugins/SKILL.md).

**Главный принцип: почти любой аспект Hyper расширяется плагинами.** Плагин приносит реализации в виде файлов `$<keyword>_<name>.*`. Загрузчик этого вида (`$loader_<keyword>.ts`) определяет, что означает декларация, как её проверить, зарегистрировать и вызвать. Сам плагин может принести загрузчик *нового* вида; встроенные виды и их контракты не подменяются произвольно. Для разных возможностей это страницы, виджеты, Canvas, инструменты, маршруты, хуки, настройки и дальнейшие точки расширения — не одна универсальная система событий.

**Включение и конфигурация — разные действия.** Пользователь включает или выключает *плагин целиком* через реестр подключённых корней (`workspace.json.pluginRegistry` в opt-in режиме; legacy declarations — пока другой путь). Только включённый корень сканируется и импортируется. Затем включённый плагин объявляет свои ключи файлами `$setting_<key>.ts`; пользователь задаёт значения через UI/БД либо через файлы экземпляра `~/.hyper/settings/$settings_<module>.json`. Значения `$settings_` не устанавливают код и не являются переключателем монтирования. Секреты хранятся отдельно. Изменение состава плагинов в текущем opt-in режиме требует перезапуска; значения файлов настроек обновляются без него.

**Единица распространения — plugin-bundle.** Bundle может содержать один или несколько плагинов; каждый плагин остаётся самостоятельным деревом исходников и единицей подключения и настройки. Пользователь ищет и получает bundles через несколько источников/HyperHubs: Git, файл или архив по HTTP, специализированный реестр или npm. Способ поиска и получения — реализация провайдера (`$plugin_provider_<id>.ts`), а не свойство runtime-плагина. Провайдер фиксирует источник и неизменяемую ревизию bundle и доставляет файлы в staging; затем общий путь: проверка всего bundle → просмотр изменений каждого входящего плагина → согласие → подготовка → подключение выбранных плагинов. Обновление одной общей Git-поставки проверяет весь checkout, включая выключенные плагины; доставка не запускает код и не включает плагины сама. Контракт провайдера и нынешние ограничения см. в [plugin-providers.md](plugin-providers.md); атомарность обновления нескольких плагинов — открытый вопрос.

## 1. Плагин — дерево исходников, а не второй runtime

Сохраняем процедурную модель: один файл — одна функция или декларация. Обычные функции вызываются через `ctx.fns`, без импорта между проектными файлами; `$<keyword>_<name>.*` интерпретируется загрузчиком своего вида. `procs` обнаруживает корни, классифицирует файлы и запускает загрузчики; прикладной `plugins` показывает каталог, проверяет кандидата и организует согласие; провайдер доставки получает исходники, но не исполняет их. Не переносим в Hyper целиком Cordis или иной сторонний фреймворк.

## 2. Один владелец у каждого вклада

Функция, HTTP-маршрут, страница `$app_`, виджет `$widget_`, вид Canvas `$canvas_`, инструмент `$tool_`, настройка, hook и новый тип файла должны быть привязаны к корню плагина и его поколению. По этому владельцу строятся карточка плагина, диагностика конфликтов и в будущем выгрузка. Не определяем владельца по URL или сходству имён. Карточка перечисляет пользовательские страницы, виджеты и Canvas отдельно от технических маршрутов.

## 3. Точки расширения имеют явный контракт

У каждой точки определены тип входа и ответа, право только наблюдать / преобразовать / запретить / выбрать исполнителя, порядок обработчиков, значение «не обработал», таймаут, отмена и поведение при ошибке. Для политики безопасности ошибка должна закрывать действие, а для необязательного наблюдателя — не останавливать ход, но быть видимой. Не используем универсальный hook с неоговорёнными побочными эффектами.

## 4. Несколько обработчиков и один исполнитель — разные задачи

Событие может иметь несколько подписчиков; заменяемая роль имеет одного явно выбранного провайдера. Конфликт провайдеров не разрешается молчаливым порядком сканирования. Зависимости и отсутствие обязательного провайдера диагностируются до выполнения работы. Реализации по умолчанию остаются доступными без плагинов.

## 5. Минимальное ядро, расширяемые реализации

Почти любой аспект продукта должен допускать вклад плагина через собственный `$<keyword>_`-контракт: интерфейс, агент, модель, инструменты, интеграции и хранение. Ядро должно обеспечивать обнаружение и исполнение деклараций, а не владеть всеми реализациями. Даже Postgres, очередь и доставка HTTP могут получить альтернативные реализации, если для них определён контракт; текущие реализации остаются значениями по умолчанию. Инварианты надёжности — атомарный захват работы, отсутствие потери сообщений, восстановление после сбоя — обязательны для любой реализации. Не объявляем `agent.run` или конкретную БД навсегда незаменяемыми.

## 6. Видимое модели — восстанавливаемо

Изменение промпта, контекста, аргументов и результата инструмента, влияющее на модель, должно быть воспроизводимо из сохранённого состояния или журнала хода. Эфемерные наблюдатели могут не писать в БД; решения, меняющие продолжение и безопасность, должны оставлять диагностический след. Не допускаем расхождения между тем, что увидела модель, и тем, что показывает история.

## 7. Установка, запуск и выгрузка — разные операции

Отключённый плагин не импортируется. Загрузка кода означает доверие; скачивание исходников не должно запускать их. Hot reload функции сейчас не равен безопасной выгрузке плагина: top-level эффекты, подписки, таймеры и незавершённые вызовы не откатываются сменой реестра. Пока нет owner-aware dispose, draining и контроля durable jobs/triggers, интерфейс не обещает hot unload и при необходимости требует перезапуск.

## 8. Расширяемость должна быть проверяемой

Для каждой точки — пример плагина и тесты: нет обработчика, несколько обработчиков, конфликт исполнителей, ошибка, отмена, повтор, reload и восстановление после перезапуска. Обязательны диагностируемые владелец и причина отказа. Двигаемся от одного сквозного сценария (контекст → запрос модели → проверка инструмента → сохранённый результат), а не от списка из десятков пустых hook-имён.

## Что взято у других

- **Pi:** раздельные типизированные события, явные права обработчиков и политика ошибки для вызова инструмента.
- **DeepSeek Harness:** интерфейс роли/провайдера, зависимости и идея owner-aware очистки регистраций; без переноса Cordis как обязательного ядра.
- **OpenCode:** отдельные точки для контекста, запроса модели, инструментов и сжатия.
- **OpenHands SDK:** пакетирование навыков, команд, агентов, MCP и hooks в одном поставляемом плагине.
- **Goose и Codex:** совместимость с MCP и ограниченные, понятные точки проверки действия до выполнения.

Открытые решения: каким именно `$<keyword>_`-контрактом заменять `agent.run` и инфраструктурные реализации; обязателен ли полный журнал изменений модельного контекста; как версионировать контракты точек; когда делать полноценный hot unload. Эти решения не считаются принятыми только потому, что они описаны здесь.
