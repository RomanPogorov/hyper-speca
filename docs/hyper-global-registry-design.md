# Hyper Global Registry: имена и доставка plugin-bundles

**Статус:** черновик для обсуждения, не реализованный протокол и не план миграции без отдельного решения. Связанные документы: [принципы расширяемости](plugin-extension-principles.md), [провайдеры источников](plugin-providers.md), [нынешний hyper-git registry](plugin-registry.md), [runtime и lifecycle](plugin-runtime-architecture.md).

## Задача

Дать plugin-bundle стабильное, узнаваемое имя, которое не зависит от GitHub, HyperHub, npm или URL файла. Разработчик может публиковать версию через разные источники, а пользователь — искать bundle по имени, видеть владельца и проверять, что установлена ровно одобренная ревизия. Сам каталог не должен запускать код и не должен требовать собственного хранилища архивов.

## Термины и границы

- **Plugin-bundle** — единица распространения и обновления, включающая один или несколько самостоятельных плагинов. Их исходники содержат декларации `$<keyword>_<name>.*`; включение и `$setting_`-конфигурация относятся к отдельным плагинам после установки. Отключённые плагины внутри bundle не должны монтироваться.
- **Hyper Global Registry (HGR)** — публичный каталог имён, владельцев, версий и проверяемых указателей на содержимое. Он выдаёт и резервирует имя, проверяет право публикации, подписывает или иным образом аутентифицирует запись каталога. Не исполняет bundle.
- **Source provider / HyperHub** — адаптер для поиска и получения конкретного содержимого: Git, HTTP-архив/файл, npm или собственный реестр. Существующий `$plugin_provider_<id>.ts` — точка интеграции источника; каталог имён не обязан заменять этот интерфейс.
- **Plugin manager** в экземпляре Hyper — review, согласие, staging, установленное состояние и переключение runtime. `procs` — сканирование файлов и загрузка деклараций. Сетевая доставка не должна напрямую менять runtime-реестры.

## Идентичность и владение

Каноническое имя bundle: `@scope/name`, например `@health-samurai/clinical`. Имена нормализуются по единому опубликованному правилу (допустимые символы, регистр, Unicode, длина); до утверждения этого правила имена не считаются совместимыми с npm только из-за похожего синтаксиса. `scope` принадлежит зарегистрированному субъекту — человеку или организации; он может делегировать роль издателя. Одинаковое название из другого HyperHub не получает это имя автоматически. Пользователь видит **издателя**, **источник** и **уровень подтверждённости**, не одно лишь красивое имя.

Передача scope или bundle другому владельцу — отдельная подтверждаемая операция с журналом и уведомлением установленных экземпляров; ранее опубликованные записи и их digests не переписываются. Удаление публикации скрывает её из поиска, но не переименовывает чужое содержимое и не стирает историю установки. Для освобождения заброшенных имён, споров и удаления незаконного содержимого потребуется отдельная политика управления — не отдаём имя автоматически по истечении таймера.

## Версии, адреса, целостность

Публикация связывает `(canonicalName, version)` с **неизменяемой** ревизией источника и digest проверяемого содержимого. Версия нужна для выбора/совместимости; реальную идентичность установки задают имя, источник, точная ревизия и digest. Повторно опубликовать тот же номер версии с другими байтами нельзя: выпускается новая версия; при компрометации запись можно отозвать с явной причиной. В первой версии допустим один основной источник и список эквивалентных зеркал только при совпадении digest.

Git-ссылка указывает полный commit и путь к bundle в дереве; HTTP — неизменяемый URL и digest скачанного артефакта; npm — точную версию и digest tarball. Digest для bundle с несколькими плагинами считается по каноническому набору файлов и путей после распаковки; формат нормализации, ограничения путей, symlinks и размер должны быть опубликованы до реализации. Git commit сам по себе недостаточен: force-push может сделать объект недоступным; зеркало допустимо только с тем же digest.

Черновик записи каталога (не готовая API-схема):

```json
{
  "name": "@health-samurai/clinical",
  "version": "1.2.0",
  "publisher": "org:health-samurai",
  "bundleDigest": "sha256:<hex>",
  "plugins": [{ "id": "clinical", "path": "plugins/clinical" }, { "id": "vitals", "path": "plugins/vitals" }],
  "source": { "kind": "git", "url": "https://github.com/health-samurai/clinical.git", "commit": "<full-commit>", "path": "." },
  "status": "active"
}
```

Публичный URL bundle — указатель для получения, а не идентичность автора и не доверие к коду. Аутентичность ответа каталога должна проверяться независимо от ответа источника; способ подписи, управление ключами и восстановление после компрометации — отдельная спецификация.

## Поток публикации

1. Издатель получает `scope` и право публикации в нём; подтверждает контроль над аккаунтом. Владение GitHub-репозиторием или npm-пакетом само по себе не даёт права на чужое имя HGR.
2. Провайдер источника фиксирует точную ревизию, получает содержимое в изолированный staging и проверяет состав bundle **как данные**, без импорта TypeScript, package scripts и автоматической установки зависимостей.
3. HGR проверяет право издателя, структуру записи, уникальность `(name, version)` и digest; публикует неизменяемую запись. Продвижение тега `latest` меняет указатель, но не опубликованную версию.
4. Отзыв или смена источника требуют журналируемой операции. Заменить URL допустимо лишь при подтверждении тождественного содержимого; иначе выпускается новая версия.

## Поток поиска и установки

```text
Поиск в HGR / HyperHub → выбор @scope/name@version
    → resolve: владелец + digest + точный источник
    → source provider materialize в staging → проверка digest
    → список плагинов, прав, зависимостей и diff → согласие пользователя
    → сохранение lock-записи → подготовка отдельно от load
    → включение выбранных плагинов → runtime-загрузка
```

Экземпляр хранит lock-запись с каноническим именем, версией, publisher, provider, URL/координатами, точной ревизией, digest, составом bundle и выбором включённых плагинов. Нельзя принимать изменение digest «на той же версии» автоматически. Offline запуск опирается на уже проверенные локальные файлы; при исчезнувшем источнике уже установленный bundle не подменяется похожим именем с другого сервера.

Обновление всего bundle сначала подготавливается и проверяется в staging; пользователю виден diff **всех** входящих плагинов, в том числе выключенных. Грязный checkout не очищается автоматически. После согласия происходит переключение с возможностью отката; гарантию атомарной выгрузки/обновления работающего runtime не обещаем, пока не появятся owner-aware cleanup, draining и остановка фоновых задач (см. [plugin-runtime-architecture.md](plugin-runtime-architecture.md)). На первом этапе может потребоваться перезапуск.

## Совместимость и этапы

Нынешний `hyper-git` registry индексирует плагины по `(repo, name)` из default branch и возвращает commit; это **не** HGR и не глобальная выдача `@scope/name` для bundles. Текущий интерфейс source provider работает с кандидатом-плагином; поддержка multi-plugin bundle потребует версии его контракта или нового слоя композиции. Не переименовываем молча существующие установки: старые координаты остаются действительными, а привязка к HGR имени предлагается отдельно и требует подтверждения совпадающего содержимого.

1. Зафиксировать нормализацию имён, правило владения и канонический digest bundle; составить примеры атак и тесты.
2. Выпустить HGR как read-only каталог + публикацию с авторизацией; Git/HyperHub — первый источник. Не включать автоматическую установку.
3. Добавить `resolve` и lock-запись в plugin manager, review всего bundle и явный выбор плагинов; проверить миграцию существующих установок.
4. Подключать HTTP/npm провайдеров без изменения идентичности bundle. Только после этого решать hot update/unload.

## Открытые вопросы

- Кто управляет HGR и выдаёт `scope`: команда Hyper, федерация реестров или отдельные организации? Как передаются права и обрабатываются споры?
- Как именно HGR аутентифицирует записи и распространяет отзывы при недоступности сервера?
- Включение/обновление multi-plugin bundle атомарно или допустимо частичное состояние? Как сохранять настройки и незавершённые задания при откате?
- Где граница bundle для Git monorepo: весь checkout или объявленный подкаталог? Как идентифицировать неизменяемый набор файлов одинаково для Git, HTTP и npm?
- Как выражать совместимость с версией Hyper, зависимости bundles и требуемые полномочия, не выполняя код на этапе поиска?
