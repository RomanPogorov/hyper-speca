# Десять архитектур плагинов рядом с Hyper

**Статус:** исследовательский отчёт для обсуждения, не спецификация Hyper. Сверено с официальными материалами десяти систем и локальными исходниками Pi / DeepSeek Harness; ссылки в каждом разделе. Архитектуры и доступные API меняются, поэтому приведены механизмы, а не обещание совместимости. Наши исходные принципы: [plugin-extension-principles.md](plugin-extension-principles.md), доставка и lifecycle: [plugin-runtime-architecture.md](plugin-runtime-architecture.md), каталог имён: [hyper-global-registry-design.md](hyper-global-registry-design.md).

## Ось сравнения

Смотрим на пять вопросов: **(1)** что распространяется — одна реализация или bundle; **(2)** как объявляются виды вкладов; **(3)** кто вызывает реализацию и управляет зависимостями; **(4)** можно ли обновить/выгрузить без хвостов; **(5)** кто отвечает за поиск, доверие и включение. Наличие аналогичного API не означает, что система поддерживает замену всего своего ядра.

| Система | Единица поставки | Объявление и вызов | Сильная сторона | Граница относительно Hyper |
|---|---|---|---|---|
| Directus | extension или bundle | Тип расширения; клиентские и серверные entrypoints | Bundle из разнородных расширений | Предопределённые типы; не произвольный `$loader_` |
| Grafana | panel, datasource, app | `plugin.json` и API типа | App объединяет панели и источники | UI/данные — основной домен |
| OpenClaw | npm/локальный plugin | Manifest + runtime регистрации | AI-каналы, инструменты, модели, hooks | Регистрация API, не файловая грамматика Hyper |
| Backstage | backend plugin + module | Extension points и dependency injection | Контракт владельца точки и потребителя | Композиция главным образом при запуске |
| VS Code | extension | `package.json.contributes` + активация кода | Декларация до исполнения, extension host | Host не равен sandbox, код расширения доверенный |
| Obsidian | plugin | `onload` + `register*` | Очистка слушателей и ресурсов | Персональное приложение, нет bundle-контракта |
| Strapi | plugin | Backend/admin entrypoints + lifecycle | Разделение регистрации и запуска | Состав и конфигурация в основном на старте |
| Jenkins | plugin (Java) | `@Extension` реализует интерфейс | Строгие типы точек и реестр реализаций | Java/серверная модель, не файловые декларации |
| Pi | extension | `ExtensionAPI`, `pi.on`, `register*` | Точные точки внутри цикла агента | Стандартный цикл в ядре |
| DeepSeek Harness | дерево плагинов/профиль | Cordis services + events + effects | Заменяем даже agent loop | Значительная стоимость lifecycle и зависимости |

## 1. Directus — типы расширений и bundle

**Поставка.** Directus различает API-расширения (например, hook на события и endpoint для HTTP) и расширения интерфейса (modules, panels, interfaces, displays, layouts, operations). Bundle содержит несколько расширений как один поставляемый пакет; `directus:extension.entries` в `package.json` объявляет содержимое. Платформа загружает entrypoint согласно типу расширения, а не просто импортирует любой файл как универсальный плагин.

**Что взять.** Это наиболее близкий пример к нашему разделению *bundle как единицы доставки* и *отдельных `$<keyword>_`-реализаций внутри*. На карточке поставки следует показать всё, что входит в bundle, а на карточке каждого плагина — его страницы, Canvas, виджеты, функции и инструменты. **Что не копировать:** жёстко закрытый список видов вкладов: у Hyper плагин может принести загрузчик нового вида, если его собственный контракт проходит проверку.

Источники: [Extensions Overview](https://docs.directus.io/extensions/introduction/), [Bundles](https://docs.directus.io/extensions/bundles).

## 2. Grafana — app как контейнер разных возможностей

**Поставка.** Метаданные `plugin.json` определяют тип и идентичность. Panel рисует визуализацию, datasource получает данные, app предоставляет навигацию и страницы и может объединять панели и источники в одну установку. Бэкенд app может обслуживать серверные вызовы отдельно от frontend-кода. Это не один универсальный hook — роли имеют разные требования к реализации.

**Что взять.** Различать в каталоге *контейнер и его состав*: «установлен app» не отвечает на вопросы, какие панели или страницы доступны. Разделение браузерной и серверной ответственности полезно для `$app_`, `$widget_`, `$canvas_` и `$route_`. **Ограничение:** предметная область Grafana уже и не даёт готовый протокол заменяемого agent loop.

Источник: [Anatomy of a plugin](https://grafana.com/developers/plugin-tools/key-concepts/anatomy-of-a-plugin).

## 3. OpenClaw — широкие плагины AI-хоста

**Поставка и вызов.** Плагин с manifest и исполняемым entrypoint может регистрировать инструменты агента, messaging channels, провайдеры моделей, hooks и другие возможности. Поиск/установка и разрешение на выполнение не тождественны: важно знать, какой код будет загружен и какие возможности он приносит. OpenClaw показывает, насколько широко может быть расширен именно AI-продукт без изменения каждого исходного модуля.

**Что взять.** Инвентарь вкладов должен отвечать «что принёс плагин?» для модели, каналов, инструментов и UI, а не только показывать число функций. **Не переносить буквально:** императивный способ регистрации, если файловая декларация `$<keyword>_` уже даёт Hyper более локальный и индексируемый контракт.

Источники: [Building plugins](https://docs.openclaw.ai/plugins/building-plugins), [Plugin manifest](https://docs.openclaw.ai/plugins/manifest).

## 4. Backstage — владелец extension point и модули-поставщики

**Поставка и зависимости.** В новой backend-системе plugin владеет extension point; backend module зависит от этой точки и добавляет поведение при инициализации. Module может отвечать за интеграцию с определённым plugin, не изменяя исходники последнего. Dependency injection определяет порядок запуска; модуль, предоставляющий вклад, готовится до инициализации его потребителя. Frontend-композиция отдельно связывает routable extensions с приложением.

**Что взять.** `$point_` должен описывать контракт владельца, `$hook_` — указывать точку, которую он реализует; диагностика обязана называть и владельца точки, и плагин-поставщик. Зависимости лучше проверять до активации, а не получать исключение при первом пользовательском запросе. **Ограничение:** эта композиция больше про предсказуемый запуск, чем про гарантированную динамическую выгрузку.

Источники: [New Backend System](https://backstage.io/docs/plugins/new-backend-system/), [Composability System](https://backstage.io/docs/plugins/composability/).

## 5. VS Code — декларативный вклад и отложенная активация

**Поставка.** Extension manifest `package.json` объявляет contributions: команды, меню, views, языки, темы и многое другое. Хост может показать часть возможностей до исполнения entrypoint, а код активируется по соответствующему событию. Extension host отделяет выполнение расширений от UI-процесса; где именно работает код (локально, удалённо, в web) определяется его возможностями и окружением.

**Что взять.** Развести просмотр *деклараций* до запуска и фактическую активацию; каталог Hyper Global Registry может безопасно индексировать метаданные без импорта TypeScript. Подумать об отложенной активации только там, где она не ломает порядок загрузчиков. **Предостережение:** отдельный процесс повышает устойчивость UI, но сам по себе не делает расширение безопасным или автоматически выгружаемым.

Источники: [Contribution Points](https://code.visualstudio.com/api/references/contribution-points), [Activation Events](https://code.visualstudio.com/api/references/activation-events), [Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host).

## 6. Obsidian — понятная жизнь экземпляра плагина

**Поставка и lifecycle.** TypeScript-плагин получает экземпляр `Plugin`, запускает регистрации в `onload` и имеет `onunload`. Регистрации через `registerEvent`, команды и другие API имеют управляемую платформой очистку; документация рекомендует использовать эти механизмы вместо сторонних обработчиков, о которых runtime не знает.

**Что взять.** Каждая регистрация Hyper должна принадлежать конкретному поколению плагина; при выключении должны прекратиться подписки и фоновые задачи. Не считать повторный import реализацией unload. **Ограничение:** простота Obsidian не переносит автоматически остановку in-flight agent turns и durable jobs — их нужно отдельно drain/cancel и согласовать с БД.

Источники: [Plugin API](https://docs.obsidian.md/Reference/TypeScript+API/Plugin), [Plugin guidelines](https://docs.obsidian.md/Plugins/Releasing/Plugin+guidelines).

## 7. Strapi — раздельные фазы и серверные составляющие

**Поставка.** Backend-плагин экспортирует routes, controllers, services, policies, middlewares, content types и config. Lifecycle разделён на `register` (регистрация), `bootstrap` (работа после регистрации) и `destroy` (остановка). Отдельный admin entrypoint отвечает за интерфейс. Конфигурация плагина валидируется отдельно от реализации.

**Что взять.** Для Hyper различать *декларацию → подготовку → запуск → остановку*, а также настройки плагина и включение плагина. Миграции, установка зависимостей и внешние побочные эффекты не должны тайно происходить во время discovery. **Ограничение:** сам lifecycle Strapi не является гарантией атомарного live-update; наши условия ошибочной остановки и отката требуют отдельной спецификации.

Источники: [Server API for plugins](https://docs.strapi.io/cms/plugins-development/server-api), [Plugin structure](https://docs.strapi.io/cms/plugins-development/plugin-structure).

## 8. Jenkins — контракты extension points как главный API

**Поставка.** Core и плагины определяют Java interface или abstract class как extension point. Другие плагины дают реализацию и помечают её `@Extension`; runtime обнаруживает реализации. Это классическая модель «владелец интерфейса — отдельный поставщик». Update Center распространяет плагины, но распределение и вызов реализаций остаются разными задачами.

**Что взять.** Для `$<keyword>_` фиксировать контракт payload, результата, ошибок, порядка и возможности нескольких реализаций. Не путать hooks с заменяемыми single-provider ролями. **Ограничение:** большое число extension points повышает стоимость совместимости: изменение контракта отражается на независимых плагинах.

Источники: [Extensions Index](https://www.jenkins.io/doc/developer/extensions/), [Plugin Development](https://www.jenkins.io/doc/developer/plugin-development/).

## 9. Pi — детальные перехваты в стабильном agent loop

**Поставка и вызов.** Extension — TypeScript-фабрика, получающая `ExtensionAPI`. Она регистрирует tools, model providers, slash-команды и обработчики `pi.on()`. События разведены по семантике: некоторые только наблюдают, `tool_call` может изменить аргументы или запретить вызов, `tool_result` преобразует ответ, `before_agent_start` влияет на системный промпт и набор инструментов, события сессии сопровождают fork/compact/shutdown. Обработчики вызываются по порядку; ошибка в защитном `tool_call` блокирует инструмент. Сам стандартный цикл агента при этом остаётся в Pi.

**Что взять.** Явно различать «наблюдать / изменить / запретить», описывать ошибки и параллелизм вызовов. Такой API можно применить к `$point_`/`$hook_` Hyper без немедленной замены `agent.run`. **Чего недостаточно для нашего принципа:** Pi не показывает, как сделать сам цикл плагином.

Источники: [Pi extensions](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md), локально `~/pi-mono/packages/coding-agent/src/core/extensions/types.ts`.

## 10. DeepSeek Harness — композиция заменяемых сервисов

**Поставка и зависимости.** Cordis-композиция из профилей, bundles и конфигурационных patch-слоёв монтирует дерево плагинов. Плагин может предоставить сервис (`ctx.llm`, `ctx.tools`, `ctx.sessions`, `ctx.agentLoop`), а потребитель объявляет `inject`; пока обязательного сервиса нет, потребитель не активируется. Events имеют разные dispatch modes (`emit`, `parallel`, `serial`, `waterfall`). Регистрации и ресурсы принадлежат plugin fiber и снимаются при выгрузке; исчезновение обязательного сервиса выгружает зависимых потребителей. Даже цикл агента — заменяемый plugin.

**Что взять.** Описать single-provider роли отдельно от multi-handler событий, учитывать зависимость и владельца каждой регистрации, обеспечить вывод причины `pending` или отказа. Если заменяем агентный цикл целиком, его контракт должен включать сессию, отмену, поток, состояние и восстановление. **Что не переносить без необходимости:** Cordis и всю модель fibers; Hyper уже имеет `ctx.fns`, файловую грамматику и собственный runtime.

Источники: [Architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md), [Services](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-tutorial/03-services.md), [Lifecycle and effects](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-tutorial/02-lifecycle-and-effects.md), локально `~/deepseek-harness`.

## Вывод: дизайн для Hyper

1. **Единица поставки — bundle; единица включения — плагин.** Источник (Git, HTTP, npm/HyperHub) и глобальное имя не определяют способ исполнения. Для каталога сначала читаются inert-декларации, а установка и запуск требуют проверки и согласия.
2. **Файловая грамматика — общий механизм расширения.** `$<keyword>_<name>.*` находит loader; каждый loader владеет контрактом, индексом регистраций, диагностикой и безопасной выгрузкой. Встроенные виды нельзя перекрыть случайно, новые виды могут прийти с плагином.
3. **Граница плагина и карточка.** Каждый вклад имеет владельца root+generation. Карточка показывает список страниц, виджетов, Canvas, tools, routes, функций и hooks; статистика маршрутов не подменяет список страниц.
4. **Контракты важнее числа hooks.** Для каждого расширения указать тип роли (событие или один провайдер), вход/выход, порядок, ошибку, таймаут и судьбу in-flight работы. Обновление и выгрузка требуют owner-aware disposal; пока их нет — честно показывать необходимость рестарта.
5. **Выполнение по этапам.** Сначала инвентарь вкладов и read-only review bundle, затем пара узких точек в агенте, затем lifecycle регистрации и только потом замена больших сервисов. Не объявлять существующий reload полноценной выгрузкой.

**Вопросы для решения:** нужно ли допускать новые loaders от сторонних плагинов без дополнительного доверия; какие контракты стабильны публично; единица атомарного обновления (один плагин или весь bundle); как сохранять семантику уже начатого agent turn при обновлении; кто подтверждает права публиковать под глобальным именем.
